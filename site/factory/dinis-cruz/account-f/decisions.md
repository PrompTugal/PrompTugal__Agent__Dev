## 2026-11-26: the deploy-speed proposal (for Dinis, before I change CI)

Measured by the conductor on 26 Nov (run 45735222327): about 11 minutes a push; validate job 5 min, release job 4 min; the site is 2,471 pages and 26,000 files, built and gated twice. Never weaken a check.

What the workflow does today (`.github/workflows/deploy-pages.yml`, read on 26 Nov): `validate` builds and runs `newsroom/build/validate.js` on the pushed commit; `release` (needs validate) runs `tag_release.sh`, which numbers, rebuilds and runs the gate again on the numbered tree *before* it commits or tags, then rsyncs and deploys.

1. **Drop the duplicate gate on dev pushes (recommended first).** The gate in `tag_release.sh` already runs on the exact tree that ships, before anything is committed, tagged or deployed, so a red tree is never numbered. The `validate` job on a dev push is the same gate on almost the same tree. Keep `validate` for pull requests, `work/**` and `main` (where there is no release), and let the dev release job run alone. Saves about 5 minutes; no check removed (the gate runs once, on the shipping tree). Risk: a red push now fails in the release job, not in validate; the failure is as visible. Needs a trial run to confirm the 11 minutes become about 6.
2. **Build once.** The version is written into every page, so a pre-numbered build cannot be reused as is. Options: (a) as 1; (b) make the version a post-build step (a small substitution over the output) so validate's tree is the release tree; (b) is bigger and changes the build, so not first.
3. **Board-only commits skip the site build.** Split the gate into checks that need the built pages and checks that read only source and data (schemas, keys, status files). A commit touching only `board/` (and `history/`-style files) runs the second group. The site must still deploy because `/board/` is served; for that, reuse the previous release's built tree and overlay `board/`. Needs care; second.
4. **Move the board out.** The board served at promptugal.news/board/ is most of the churn. Each agent's home repository now holds its own state (as this one does); once agents write there, board-only pushes to the website stop. This is the conductor's and Dinis's plan; I help by making the website's board read-only for agents as they move.

Asking Dinis: yes to 1 (I will try it on a branch and report the measured time), and which of 3 and 4 first.

## 2026-11-26 12:00Z: proposal: article translations on the site and in the app (for cl-6.translator, cl-6.security, cl-6.conductor)

What exists (read in newsroom/build/features/by-place.mjs): the translation memory is `data/i18n/tm/<culture>/*.json`, keyed by the first 16 hex of sha256 of the NFC, space-collapsed English (so a string is translated once and reused), each entry `{t: ...}`; `segmentsOf()` makes segments from the place files only; the API has `api/v1/i18n/segments.json` (id to English), `queue/<culture>.json` (what the memory lacks) and `<culture>/index.json` (which place pages exist); place pages exist per culture at `/<culture>/<place path>`. Nothing reads an article. There is no per-culture file of translations the app can read.
Proposal, in two phases, each through cl-6.security:
1. **API (small).** (a) An article segmenter in the same module: per article, the title, summary, each heading and each paragraph or list item as a segment, ids `article:<slug>#<n>`, text as in the markdown with inline links kept (the translator's check keeps placeholders, URLs and numbers); code blocks and tables skipped. (b) They join `segments.json` and the queue files. (c) A new per-culture file `api/v1/i18n/<culture>/segments.json`: `{<id>: {t: translation, ok: reviewed?}}` for every segment (place and article) the memory holds; a missing id means: fall back to English for that segment, as the pages do. The app reads that file plus `segments.json`. (d) The gate's memory checks (placeholders, URLs, numbers) cover the article segments.
2. **Pages (bigger, later).** `/<culture>/articles/<slug>.html` per culture with at least a minimum share of the article translated, each translated paragraph in `lang="<culture>"`, a visible 'machine-translated, not yet reviewed' note while ok is false, the English original linked, and the article's own signature note unchanged (the signature is over the English twin; a translation is a derivative, never signed as ours).
Need from cl-6.translator: (i) the segmentation rule you used for the 96 article segments (so mine produces the same texts and the same keys); (ii) your pt-PT memory for the six 26 Nov articles on dev (branch work/cl-6.translator, 2869484d6): memory files are data, so they should reach dev by your own signed commit into data/i18n/tm/ (I cannot take them from a branch; the same signed-commit rule as the place data would do, if you want it); (iii) the launch cultures for the app (you recommend en-GB and pt-PT). Rights: article text is ours (CC BY 4.0, code Apache-2.0); a translation is a derivative under the same licence with the machine-translation label; items quoted from other sources keep their terms (cl-6.rights to confirm).

## 2026-11-26: A7, a gate check that a website commit stays in its signer's ABP paths (proposal, a warning first)
Asked by cl-6.security's access review via the conductor. Not built; the design is for cl-6.security to weigh.
- **What it checks:** for each commit on the first-parent line after a pinned baseline, the files it changes must all match the write paths of the agent whose key signed it, as the ABP grants them (abp/<agent>.md, "writes (repository)"). A file outside them is reported with the commit, the agent and the path.
- **Who signed:** the commit's SSH signature verified against the agent's active key in board/keys.json as it stood in the parent (the same walk as the keys.json check, lib/keys-changes.mjs). An unknown key is reported, not guessed.
- **Where the paths come from:** the ABP policies live in PrompTugal__Agent__ABP, not here, and the gate must be offline. So a signed snapshot, newsroom/tools/abp-paths.json ({agent: [globs]}), made by a small sync tool from the raw policies and committed by a dev or conductor key, under the signed-root check (as place-signers.json). The gate reads the snapshot only. Refreshing it is a change security reviews.
- **Warning first, then error:** a WARN until the snapshot has held for a day with no false positive, then an error. Files the CI itself commits (site vX.Y.Z by GitHub Actions: version.txt, versions.json, REALITY.md) are exempt by name; so are merge commits.
- **Known gaps:** a shared-root-key agent (an old *.dinis agent with a path policy not in the ABP) has no entry and is reported as unknown; a path the ABP does not list but the conductor routes (their relay) shows as a violation until the policy is widened, which is the point.
- **Needs from others:** cl-6.abp: a machine-readable paths list per policy (JSON), so the sync does not parse prose. cl-6.security: yes or no to the design.
